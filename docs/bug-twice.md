
Bug001
复现步骤：

1. 输入内容识别出表单，手动把金额改成负数，触发校验拦截。

2. 不刷新页面，直接在消费描述框输入新内容，再次点识别文字。
预期：新识别结果覆盖表单，更新成新的金额和信息。
实际：表单保留之前那个非法的旧数值，不会自动刷新。只有刷新整个页面，表单才会清空恢复正常。
问题影响：用户很容易没注意到还是旧数字，误保存错误账单，有数据出错风险。
优化点：

1. 输入纯文字没有金额的时候，现在默认填 0.00。最好改成直接提示没有识别到金额，让用户补充，不要自动带出 0，容易混淆。

2. 一句话里面有多个数字的时候，现在直接拿第一个数字。可以加个提示，问用户哪一个才是实际付款的钱，避免识别错金额。

3. 类别识别不准，比如零食识别成餐饮。可以优化分类匹配逻辑。


BUG‑002：超大金额触发内部服务报错

• 复现：输入 手机 9999999999，点识别文字。

• 预期：金额范围校验，给出友好提示（如"金额过大，请核对"）。

• 实际：直接返回 Internal Server Error，识别崩溃，无业务提示。

BUG‑003：表单状态未重置，旧值残留

• 复现：先把金额改成负数被校验拦截，不刷新页面，直接输入新内容再次识别。

• 预期：新识别结果整体覆盖表单，金额更新为新值。

• 实际：表单保留上一轮非法旧值，不自动刷新；必须手动刷新整个页面才清空恢复。

BUG‑004：未来日期假成功提示（本次新增）

• 复现：日期选明天（未来日期），点保存。

• 预期：拦截并明确提示，或正常入库。

• 实际：弹绿色"已记录账单"成功标识，但明细里实际未写入。
Bug005
复现步骤：在自然语言查账输入框输入无意义内容，比如 abc56777、nihao 这类乱码。
预期：识别不出查询条件，给出友好提示，说明无法理解这个问题，不做统计。
实际：直接返回全部时间的支出合计，而且统计里面还带上了那些本来没有真正落库的未来日期账单。
影响：输入无效问句也直接输出汇总数据，统计结果本身还混入无效数据，容易误导用户
Bug006
复现步骤：一句话记账的消费描述输入 “5 分 25”，商户这一栏保持空白不填，直接保存。
预期：商户是必填项，应当拦截保存，提示填写商户。
实际：直接提示保存成功，账单里生成了记录，系统自动给配上了餐饮商户。
影响：必填校验失效，自动填充的商户和真实情况不一定相符，账单信息不准

BUG007（年份 / 时间筛选失效）
复现步骤：
1. 一句话记账输入 `奶茶 10`，识别后把消费日期调到很早之前的 2017 年，保存成功。
2. 进入自然语言查账，问题栏输入 `2017年`（或 "2017 年花了多少"），发起查询。
预期结果
识别到查询条件是 "2017 年"，只统计 2017 年这一年的账单金额并返回。
实际结果：
返回的是全部时间的支出合计，2017 年这个年份筛选条件完全没生效，没有单独给出 2017 年花了多少钱。
缺陷定性：
查账模块对 "年份" 这类时间条件解析 / 过滤失效，条件被忽略，退化成全量汇总。和之前 "这个月明天花了多少" 混加所有日期是同一类问题：**时间筛选逻辑不可靠**。
影响：按年份 / 时间段查询时，用户拿到的是全量金额，无法定位对应周期的消费。
补充* 2017 年这条本身能保存成功，属于 "允许补记过去日期"，这条不算 bug；问题出在查询筛选没按年份过滤。

无论上传什么图片（包括最容易识别的白底单行手写 "奶茶十元"），均提示 "未启用视觉模型，没法识别出内容"，图片识别完全跑不通。
